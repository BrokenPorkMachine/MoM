# VM Registry v0.5.0

VM state is stored at `<bundle>/manifest.json`, atomically written. `VMInstallState` is provisioning/installed/failed. Only installed records are launchable. A failed or interrupted install is **never** implicitly converted to installed. Discovery enumerates manifest-bearing immediate subdirectories of a user-chosen parent directory, without changing their content. No global indexing or destructive repairs are performed. Coordinated manifest, hardware, and connectivity changes use `.workspace-transaction.json`; readers recover prepared journals before loading state. Use [VM backup and restore](VM_BACKUP.md) for stopped-workspace snapshots, including external disk images and persistent guest state.

Every existing VM bundle also has a `.workspace.lock` lease. VM startup, provisioning, installation completion, backup creation, coordinated metadata commits, and hardware/connectivity saves hold this lease while they operate. It is an advisory cross-process `flock` over the whole bundle, covering firmware and auxiliary storage, TPM/EFI state, configuration, and disk-image references. A second app process receives an “already in use” failure instead of operating on the same VM. Kernel-managed locking releases ownership if the owner exits or crashes; the lock file itself is disposable metadata and is excluded from backups.

For Windows ARM records, `qemu.executablePath` and `qemu.swtpmPath` are untrusted launch requests when imported. Discovery and manifest loading do not execute them. Starting or provisioning requires explicit per-user approval of each canonical path and SHA-256; approval is not stored in the VM manifest. Startup validates QEMU 9.2+, swtpm's version response, and the `virt-9.2` machine profile. See [BACKEND_EXECUTABLE_TRUST.md](BACKEND_EXECUTABLE_TRUST.md).
